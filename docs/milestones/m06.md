**Three decisions worth the record, because each foreclosed a cheaper wrong answer.**

**1. The Pack Definition is on its own version train, and the Workspace Definition did not move.** The
session opened intending `2.5 → 2.6` with every carrier corrected. The session-open checkpoint refused
it: MINOR means "new optional slots, relaxed constraints", and none occurred —
`spec/workspace.schema.json` is byte-identical across this change. Worse, `doctor` derives the current
version from the schema's own `$id` and **refuses a manifest naming a version ahead of it**, so a
manifest bumped to 2.6 without the schema moving would have been refused outright. The bump would have
broken CI, which is the strongest evidence it was never a real instruction. `packs` items stay free
strings for the same reason: tightening them to the canonical `category/name` form is a constraint an
existing manifest could newly fail, and that is a MAJOR.

**2. Tighten-only is enforced in two places because neither half can do it alone.** The rule — a pack
may raise a tier, never demote one ([`0010`](../../.portulan/proposals/0010-prohibited-as-a-fourth-universal-tier.md),
agreed 2026-07-27) — is *relative to the tier an id already holds*, and a manifest cannot see the layer
beneath it. So the schema does the part shape can do: **`auto` is absent from the fragment tier enum**,
which makes demotion-to-unattended unexpressible in a pack at all. The relative comparison is the
compiler's, and a demotion **throws** rather than being dropped. `0013` asked only that the manifest be
"shaped so the rule is checkable rather than trusted"; this is that, with the boundary between the two
halves written down rather than implied.

**And tightening turned out to have two axes, which the pre-commit checkpoint found by attacking the
merge rather than reading it.** The first implementation compared only the tier — which is not
tighten-only. A fragment naming an existing id at a stronger tier replaced the **whole rule, including
its action**, so raising the tier while swapping the matcher passed every rank check and removed the
gate. Demonstrated against this repository's live policy: a fragment
`{id: force-push-without-a-lease, tier: prohibited, action: {none: …}}` was reported as
`tightens gated → prohibited` while the emitted `Bash(git push --force:*)` gate **disappeared** — the
workspace strictly less cautious about the exact action the rule exists to gate, with a provenance line
claiming the opposite. Rule ids are greppable by design and ship in `core/`, so knowing one is no
barrier. A fragment naming an existing id must now carry that rule's action unaltered; a pack wanting to
gate something else contributes a new id. The tier is compared first, so a demotion is still reported as
a demotion. **This is the second time a fresh context has found a hole in the gate matcher's own subject
by trying to get past it rather than reviewing it**, which is the checkpoint's argument restated as
evidence — the first is recorded in
[`.portulan/compile/README.md`](../../.portulan/compile/README.md).

**The same checkpoint caught a condition-4 violation inside the change that introduced it.** The Pack
Definition asserted, normatively, that "`doctor` refuses a manifest naming a version ahead of the one it
implements" — and nothing implemented it, while `doctor` cheerfully printed *"validates against Pack
Definition 99.0"*: a conformance claim about a contract it had never seen. The refusal is now built, on
the pack train's own `$id`, symmetric with the workspace train's.

**3. The refusal is exercised by fixture, because nothing exercises it naturally.** The one real pack
contributes pure additions against a core layer that ships no gate policy at all, so no shipped artifact
would ever have taken the refusing branch. It is forced red across every demotion direction —
`gated → propose`, `prohibited → gated`, `prohibited → propose`, and same-tier replacement — in
[`cli/compile.test.mjs`](../../cli/compile.test.mjs). A check nobody has seen fail is a check nobody has
seen work.

**The plugin-tag obligation, re-derived — and the answer inverts the guess.**
[`the-tag-and-the-install`](../../.portulan/handoffs/2026-07-26-the-tag-and-the-install.md) recorded that
`claude plugin tag` would namespace a release as `portulan--v0.1.0`, judged that form *decorative for

its own basis had gone stale — the clone later carried the tag — so the conclusion "needs re-deriving

Definition's `portulan.version` is that day, so it was re-derived here rather than carried.

**Measured on CLI 2.1.220, 2026-07-29.** An installed marketplace is **not a git working clone at all**:
no `.git`, and the fetched tree carries a `.gcs-sha` marker instead. An install is cached at
`<marketplace>/<plugin>/<version>/`, with **several versions of one plugin coexisting** on disk, and
`installed_plugins.json` records the manifest's `version` plus a `gitCommitSha` as provenance. So a
plugin is resolved by the **version field in its manifest**, and a git tag cannot participate in that
path at all.

**The conclusion survives on a stronger basis and the reasoning is replaced.** *Decorative for
installation* was right; *because the clone carries no tags* was wrong twice over — first the clone
carried one, and now there is no clone. Tag namespacing is decorative because **installation never reads
tags**, not because of what a clone happens to hold. For a pack versioned independently of the engine,
independence is expressed by `portulan.version` in the pack manifest, which is exactly what the installer
resolves and caches by — no tag is needed for it, and none would help.

**The scope of that measurement, stated.** It was taken against the `claude-plugins-official` marketplace,
which is the only one installed on the machine that ran it; **`portulan`'s own marketplace is not
installed there**, so what is measured is the platform's mechanism rather than this project's feed
through it. That is a fact about one CLI version and re-measurement belongs on the next upgrade — the
same standing this repository gives every other host measurement. The claim it refutes was one this very
session had written into `spec/pack.schema.json` before measuring, which is corrected in the same change.

committed (so an absent location is never a finding); and it cannot be linked (so the index names rather than
links). The first two were designed for. The third was not, and CI is what noticed.

committed index was regenerated from the feed-installed pack and the equality re-derived at `41216e14` on
both carriers.
