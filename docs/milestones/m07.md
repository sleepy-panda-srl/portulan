This amendment is the sentence that names where the instantiation arrives, and it is deliberately a **row amendment rather than a core sentence**: core may not name a pack, a threshold, or a who, and every one of these three clauses is about binding exactly those.

## Amendment — 2026-07-31 (an expansion) — a composed pack's verify recipes reach the workspace

**Applied to the row.** Ruled by the maintainer at this milestone's session-open, on a question this
repository had deliberately left open rather than answered by default.

**Criterion amended with Marius, 2026-07-31, this row only — an expansion, not a narrowing, checked in the way the M1–M6 amendments established.** Added, with nothing removed: a composed pack's verify recipes reach the adopting workspace's runnable set, additive-only, namespaced by pack, never the workspace's `verify.default`. Every existing clause of row 7 stands. **Checked as an expansion:** it adds a deliverable and a demonstration to a row that already ships pack composition through `vendor`, and removes, narrows and conditions nothing.

**What was actually open, and what was not.** The Pack Definition declares four contribution kinds and
two of them are consumed by nothing —
[#140](https://github.com/sleepy-panda-works/portulan/pull/140) measured the split kind by kind:
`gates` merged by `cli/compile.mjs`, `personas` resolved and opened by `cli/index.mjs`, `skills` and
`verify` by nothing. The session-open reconciliation found that **only one of those two was still
open**. Row 7's clause (b), applied on 2026-07-30, requires a composed pack's skills to be *invocable
through a host* with parity to a core skill — which cannot be reached without reading
`contributes.skills`, so that key's consumer was already committed and the schema note saying
otherwise had gone stale nine minutes after it landed. `verify` was the live question, and it is the
one the maintainer ruled.

**Why the additive-only contract is in the row rather than in the implementation.** Because it is the
part that can be got wrong silently. A recipe that composes without limits can shadow one the
workspace declares, or become the default the Stop-gate runs, and either would mean a workspace's
green stopped being a statement about the workspace. That is a criterion-level property — it decides
what *done* means for the adopting team — so it belongs where the criterion lives.

**The limit that is NOT claimed, said plainly because the first draft of this argument overclaimed
it.** The draft argued that namespacing and the no-`default` rule stop a pack author obtaining a
code-execution path into every adopting workspace's CI. That is wrong, and the session-open checkpoint
refused it: a recipe's `run` is arbitrary shell, CI runs the recipes the manifest carries, and a
workspace that lists a pack has already consented to running that pack's code — with or without these
clauses. What the clauses prevent is the narrower thing, which is also the thing worth preventing: a
pack **silently changing what this workspace's green means**. A security claim stronger than its
mechanism is the same defect this file's neighbours are full of, one layer up.

**Then what DOES bound a composed recipe? The feed pin, and it is named in the row rather than left to
trust.** The paragraph above says what the additive-only limits are not; a reader is entitled to ask what
takes their place, and leaving that unanswered is how "not a security boundary" gets read as "unbounded".
A composed recipe is third-party code running in the adopter's CI. What bounds it is the **pin** —
milestone 6's measured discipline, where a pack resolves at a pinned version whose install files hash
byte-identical to the commit the manifest claims — not confidence in the pack's author. That is a
property an adopter can check, which is the only kind of boundary this project counts.

**And a composed recipe that cannot resolve is could-not-run, never silently absent.** Added to the row
for the same reason the verify recipes hold the three-code discipline: CI runs the recipe set the
manifest yields, so a composed recipe that quietly failed to appear would be a green computed over
something nobody ran — the false green this repository names most often, arriving through the
composition path rather than through a check. Exit 2, and the run says which pack and which recipe.

**Where it lands.** Session 2, beside the composition path `vendor` already owns — stated here because
an amendment that adds a deliverable without placing it is how a row grows an unscheduled obligation.

**Provenance.** Question 1 of milestone 7's session-open, put to the maintainer with both answers
drafted as row text — compose under a stated contract, or let declare-only stand permanently and
record it as settled rather than deferred. He ruled compose. The alternative is preserved in that
session's record rather than discarded, because the declare-only reading was defensible and a future
reader should be able to see that it was considered.

**Two clauses added 2026-07-31 after ratification, on the maintainer's instruction relayed through the
reviewing session** — the could-not-run rule and the feed-pin trust boundary above. Both **tighten** the
ruled amendment rather than reopening it: neither adds a deliverable the ruling did not already imply,
and both close a question the first draft left open (what happens when composition fails, and what
bounds a composed recipe once the limits are admitted not to). Recorded as an amendment to the
amendment rather than folded in silently, because the row is law and a change to law made after
ratification has to be visible as one.

### What the discovery clause delivered, and what it did not — the pack-root half, 2026-08-09

The pointer half landed as [#181](https://github.com/sleepy-panda-works/portulan/pull/181); this is the
other one, and it is written here so the close grades the clause against a list rather than a memory.

**Delivered.** `--pack-root auto` on `compile`, `doctor`, `index`, `init` and `vendor`, reading the same
installed-plugin record the pointer half reads — **one reader, one config directory, one record-version
refusal**, in `cli/discover.mjs`. It probes **both** shapes a plugin lands in: `<installPath>/packs` for
a repository-shaped plugin, and `<installPath>/<category>/<name>/` for a flat one, which is what this
project's own feed ships and what a first draft could not see at all. The precedence rule — **named >
discovered > derived, never union** — lives once, in `resolutionRoots`, reached through `compile.mjs`'s
`rootPlan` and called by `compile`, `doctor` and `index`; `vendor` reaches it through `doctor`, and
`init` spells its own named-wins arm because what it needs is a resolvability check before a draft is
written rather than a resolution root.

**Demonstrated against the real feed, not against its own fixtures — which is why the first draft was
wrong.** Measured 2026-08-09 on installs made by the host rather than by a test: `discoverPackRoots()`
returns the flat `portulan-checkpoints@portulan-internal 0.1.0` install as a root. It returned **nothing**
under the first draft, which knew only the repository-shaped layout, while the suite stayed green
because the fixtures encoded the same assumption as the code. Found at a pre-commit checkpoint that
looked at a real install: *a harness you write to check your own change inherits your blind spot.*

**The two verbs, reconciled rather than left opposed.** The row says discovery *"adds a root only where
none was named, and never replaces one that was"* — the object there is a **named** root. #123 says a
discovered root must not be *added* — the object there is the **`tree`-derived** root. Both hold under
one precedence rule, and neither is a union. A later session should not "fix" either sentence to match
the other.

**A NARROWING, recorded as one and flagged for the maintainer.** Discovery affects resolution **only
when asked**. The row's clause reads *"optional where discovery finds a root"*, and what shipped leaves
`--pack-root` never *mandatory* — nobody has to know the cache path — but not *optional* either. The
reason is measured: `examples/workspace.json` declares packs and no `tree`, and
[`../../.portulan/verify/doctor.sh`](../../.portulan/verify/doctor.sh) grades `examples`, so an
unasked-for discovered root made a **required recipe** read `~/.claude` on every run, and `doctor` fails
an unresolved pack where a root exists while merely noting it where none does — red locally, green in
CI. If the maintainer wants the broader default it is one branch in `resolutionRoots`, and the recipes
would need their roots pinned in the same change.

**Out of scope rather than owed.** `--repo-root` stays named-only: what it would discover is a
repository *checkout*, which no plugin record lists, and the amendment's own title names the plugin
cache. Feed authentication, any network call, and discovery of anything not installed remain excluded.

impossible rather than resolved* is true by construction, and *never becomes `verify.default`* with it.

declaring one id twice with different `run`s is schema-legal, because `contributes.verify`'s

## What the `feedback` clause delivered — D3, 2026-08-10

Written here rather than only in a pull-request body, on the same ground as the section above it: the
close grades this clause against a list, not against a memory.

**Delivered.** `cli/feedback.mjs`, dispatched by the entry point, which now builds seven of the eight.
Three verbs and the file-first design proposal
[`0014`](../../.portulan/proposals/0014-a-feedback-pipe-points-out-of-the-seam.md) argues for: `draft`
writes a report into the workspace's `feedback/` directory, `preview` prints the payload, and
`send --approve` files it through the user's own `gh` login. **No relay and no device flow** — `0014`'s
Q5(a), which needs no constitutional change; Q5(b) is a hosted service, `vision.md` permits exactly one
by name, and it stays unbuilt.

**The bytes are the same bytes by construction, not by comparison.** `preview` and `send` both call one
`payload()`, so *the payload the user saw* is not a rendering that agrees with the sent one — it is the
sent one. Two renderers that match today are two carriers of one fact.

**And the approval is bound to those bytes, which the first cut left to the flow.** The pre-commit
checkpoint found that *"a send whose exact payload the user saw first"* was, as built, a property of the
**habit** rather than of the mechanism: `send --approve` on a report nobody had previewed filed
sight-unseen, and a report edited between the two verbs filed bytes nobody had read. Both printed the
payload in the same breath, which is not the same as its having been read — nobody reads a terminal
between two lines of one command. So `preview` now stamps a digest of the payload into the report and
`send` refuses unless it matches, machine facts included, since those are in the payload too. The row's
clause is now structural. **Only `preview` stamps:** a `send` that refused for want of approval also
printed the payload, and stamping there would let a refusal manufacture the approval-eligibility it had
just declined to grant.

**The payload is a closed list rather than a filter.** Nothing here reads a workspace's name, its repo
cards, its gate map, its memory, a remote, a branch or a path; the single thing it reads out of a
workspace is `portulan.spec`, a version number. A filter enumerates what to remove and is wrong the day
something new arrives; a closed list enumerates what to include and is wrong only when somebody widens
it deliberately. The suite plants identifying material in a workspace and asserts none of it reaches the
payload.

**And no labels.** `0014` rules that the repository owns its own labels, so the form's title prefix
marks the kind. That also removes a preview/actual divergence rather than documenting one: GitHub
applies labels only for an actor with the permission to set them, so a previewed label would have been
a line the preview could not honour for most senders.

### The seam, and where fail-closed sits

**This product ships no terms.** They are client-confidential by definition, so the tool is told where a
list is: `--seam-terms` → `$PORTULAN_SEAM_TERMS` → `<workspace>/seam-terms.txt`, and the verdict names
which of the three answered. A **hit exits 1** — a scan ran and rendered a verdict — naming the term and
the section and never quoting the surrounding text, since this output reaches terminals and logs. A list
that was **named and cannot be read exits 2**, never a send. At the convention path **only `ENOENT`
means absent**, because `existsSync` answers false for `EACCES` and that is how [#166](https://github.com/sleepy-panda-works/portulan/pull/166)'s
layer at mode `0400` skipped every location it declared.

**No list configured is stated, not passed over.** The preview *and* the send print *"no term list
configured — NOTHING WAS SCANNED"* in the sentence the user approves. The alternative readings were both
worse: blocking every listless adopter would close the only inbound path an outside reader has, and
staying quiet would be a green that implies coverage it does not have.

**Ratified 2026-08-10 as a clarification rather than an amendment**, on the maintainer's close-out
instruction on this session's maintainer items and ratified by his merge of
[#206](https://github.com/sleepy-panda-works/portulan/pull/206) — the same channel and the same gate as
`0014`'s Q5. The row is marked accordingly, because every prior ruling on a criterion's reading landed
in the row's own text and a reader of `docs/plan.md` alone should meet the pointer, not the ambiguity.

**Why it is a clarification and not a narrowing**, on three grounds in this project's own documents
rather than on convenience — the strict reading is perfectly implementable, so *"we could not"* is not
one of them:

1. **The row's phrase compresses `0014`, and `0014` specifies hit-blocking, never list-existence.** Its
   design paragraph says *"a seam scan that **blocks a send it should block**"* and *"A **hit** blocks
   the send"*. D3 asks for *"a send a seam **hit** refused"*, not a listless send refused. A listless
   send has no hit and was never a send the scan should block.
2. **The seam scan is list-relative by this project's own definition.** `docs/plan.md`'s Protocol:
   *"Every session **that touched private context** runs the seam scan (**term list in the private
   context file**)."* The scan has been conditional on a seam existing since the Protocol was written.
3. **The fail-closed precedent cuts this way.** Everywhere here, exit 2 attaches to a **declared** check
   that could not run — and the tool does exactly that: a named list that cannot be read exits 2. A
   never-declared list is not a check that failed to run, and the seam list is deliberately not a
   Workspace Definition slot, so there is no declaration whose emptiness could fail closed. What averts
   the unearned green is that the disclosure lands **inside the sentence the Gated approval covers**.

**What the strict reading would have cost, named because it is the reason the ruling went the other
way:** the only non-browser inbound path would close for every adopter who keeps no seam at all — which
is most of them, and all of the ones this channel exists to hear from.

_(An earlier draft of this paragraph argued that a listless refusal would be "demanding the one artifact
this product must never hold". That is false and was struck at the checkpoint: refusing when no list is
configured requires holding no terms at all. A ratification resting on a false impossibility is the
justification-that-proves-too-much class, and the three grounds above are the real ones.)_
